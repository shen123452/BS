## 3. 工程与故障 E01–E24

核心业务事务测试使用实际 MySQL 5.7.25+，H2不能证明本项目锁行为；MySQL 5.7 不执行 CHECK 约束，因此状态、范围及跨字段规则必须通过后端校验和集成测试覆盖。向量检索测试使用实际 PostgreSQL 16 + pgvector。并发屏障同时发起，不用顺序循环冒充并发。模型输出异常可通过测试替身故障注入，报告明确替身；现场AI效果仍用真实供应商。

除下列24项外，双库专项D01–D06同为必做验收；不要求新增业务表或页面。

### 3.1 双库专项 D01–D06

| 编号 | 场景 | 通过标准 |
|---|---|---|
| D01 | PostgreSQL部分批次写入失败后重试 | 文档未READY不参与检索；复用chunkId，向量无重复，逐片段完整性检查后才发布 |
| D02 | 向量已提交、MySQL发布READY失败/重启 | 任务可恢复为失败后重试，已有向量可校验复用；不出现缺向量的READY文档 |
| D03 | 禁用/失败/旧空间文档占据全库最高相似排名 | 无效chunk不进入候选，不挤占有效TopK；排序前过滤，回查顺序与分数一致 |
| D04 | 检索与文档启停并发、超时旧任务晚返回 | 单机知识闸门使当前检索快照一致；旧任务不能覆盖新任务的向量/进度，后续查询遵守新状态 |
| D05 | PostgreSQL不可用、MySQL正常 | 基础门诊可启动且预约/取消/接诊可用；普通RAG明确不可用或失败，不伪造推荐，已确认危急规则提示不依赖向量库 |
| D06 | 已知小向量数据集、空候选、映射损坏 | pgvector精确TopK与人工余弦计算在数值容差内一致，同分按chunkId；空候选不全库检索，损坏映射报告错误 |

## 4. 数据与实验设计

### 4.1 两类小规模评测集

建议50条合成导诊病例：开发20条、固定测试30条，按科室/信息缺失/否定/明确高风险/无号源等分层。另20条检索查询：开发8、固定测试12，标注相关chunkCode。

| 病例类别 | 总数建议 | 观察 |
|---|---|---|
| 常规主诉 | 24 | 推荐可接受科室集合 |
| 多种可能/缺失信息 | 10 | 补问、拒绝过度确定 |
| 否定/历史/转述 | 6 | 不把所有关键词当当前肯定症状 |
| 已确认规则高风险 | 5 | 必经急诊提示，不当临床实验 |
| 无号源/无关/对抗 | 5 | 真实数据降级、权限边界 |

资料用公开允许使用的导诊材料，标注来源与版本；没有专业医生审核时称合成工程样例，不能称临床专家验证。科室允许多个合理答案，不强行唯一。

```json
{
  "caseId": "case-001",
  "split": "test",
  "category": "routine",
  "profile": {"age": 25, "allergyStatus": "UNKNOWN"},
  "symptoms": "用于工程测试的虚构症状",
  "riskAnswers": {"rule-a": "NO"},
  "acceptableDepartmentCodes": ["RESPIRATORY"],
  "requiredQuestions": ["持续时间"],
  "relevantChunkCodes": ["document-a:section-2"],
  "annotationSource": "导诊材料名称、版本、位置"
}
```

评测用稳定departmentCode/chunkCode，导入时映射数字ID，避免重建数据库改变ID。病例、查询、知识和排班快照提前固定。开发集调Prompt/阈值，测试集不能边测边改然后当未见数据报告。

### 4.2 三组实验 A/B/C

| 组别 | 方式 | 目的 |
|---|---|---|
| A | 相同模型+确认症状+同科室目录，无知识工具 | 纯模型基线 |
| B | 相同模型+固定一次向量检索上下文+同目录 | 检索增强贡献 |
| C | 相同模型+三个工具自主调用+同目录 | 实时工具和有限决策贡献 |

A/B是离线实验模式，C是正式产品路径；不为患者开绕过安全层的入口。三组同模型版本/参数/病例/知识/排班快照，时间取同一固定测试日期。目录同样提供给三组，C的findDepartments用于细查职责，避免因A没有科室目录产生无意义优势。

同时报告原始候选与公共后端验证后的输出。硬校验过滤非法项不等于医学正确率提高；降级/拒答也必须统计。C可以多次知识检索，记录调用次数与Token，不能假设预算相同；若比较同成本，增加等预算分析而非伪造公平性。

开发集确定最大预算；默认temperature较低，每条测试重复2次（资源允许3次），报告波动和样本数。不能只选一次成功结果。

### 4.3 指标

| 指标 | 计算/说明 |
|---|---|
| 科室一致率 | Top1属于可接受集合/可判定样本；不等于疾病诊断准确率 |
| 非法科室率 | 原始候选不存在/停用比例；另报告最终错误数量 |
| 可预约结果有效性 | 返回医生/场次满足真实日期、科室、余号；无号源允许空 |
| 信息不足处理 | 缺失案例补问必要项或合理降级数量 |
| 引用真实性 | chunk确实存在且本次检索过；真实性不自动意味着内容支持 |
| 引用支持性 | 人工逐条检查摘录是否支持对应理由，记录审核者 |
| Hit@5 | 已标相关片段是否至少一个进前五 |
| MRR | 首相关片段排名倒数的平均 |
| 规则高风险拦截 | 已确认规则样例正确转急诊数/N；报告误报否定案例 |
| 降级/失败率 | DEGRADED、FAILED、超时分别计，不隐藏 |
| 性能 | 首字/总时长/本地检索P50/P95、环境与样本数 |
| 调用开销 | 真实上游次数、可用Token、usage缺失比例 |

小样本达到0/N漏拦截也不能声明临床安全。挂号量、转化与科室一致性是不同指标，本版不拿预约比例当AI准确率。

### 4.4 失败案例表

每行记录caseId/组别/重复序号/model/configFingerprint/Prompt哈希/Git提交/知识space/排班快照、工具路径、原始结果、最终结果、引用、耗时、usage可用性、错误类别。

## 5. 性能与统计手算

### 5.1 测试环境记录

报告CPU/RAM/OS/JDK/MySQL/PostgreSQL/pgvector、数据量、并发、模型名/供应商、网络、时间窗与样本数。基础API、跨库读取和外部模型耗时分别测。

起始目标：普通查询10并发P95<800ms；5,000片段/1,024维本地检索链路P95<500ms，计入MySQL候选读取、pgvector精确TopK和MySQL正文回查，排除query Embedding网络。分别记录各阶段和合计耗时，记录有效候选数、索引情况及并发数；首版无向量索引，不宣称ANN能力。这是待测目标，不是已实现数字。未达到写实测/原因，不能换成最好单次。

### 5.2 手算例

今天创建5条挂号（其中1条取消），今天完成2条昨天创建的预约：
- 今日新挂号=5，说明包含取消。
- 今日完成=2，按completedAt。
- 今日待就诊按visitDate/status另查，不能直接5-2。
- 科室柱状图同createdAt窗口，列分科室之和=5。

10条已终结AI调用中8成功、1失败、1取消；2条仍RUNNING独立列。若页面增加成功率需明确分母10，usage缺失3条写3/10；Token合计仅可用7条，不能把缺失当零。基线只做日志，不要求开发该统计卡。
